# Cycle C — four shared operational integrations

Continues from b114252. These are four bounded implementation outcomes within the remaining original design Phases 4/7/10; they do not represent four entire design phases or release acceptance.

1. **Operational intake boundary.** Existing risk draft reads retain linked use-case operational status. Suspended/archived cases cannot assign, edit or submit new intake. A PostgreSQL parent-row lock and trigger also reject new risks and changes to unregistered intake after an authorized restriction/stop, including draft-to-submitted allocation races. Previously created drafts remain readable. Registered risk assessment, remediation, monitoring and immutable history continue through their existing governed services. This does not change shared DataAsset activity or imply the external AI application has stopped.
2. **Shared workflow severity.** Native case list/detail and task inbox/detail add a read-only `aiGovernance` projection after live explicit AIRS grants and current organization/domain/classification/own-record scope. Native PrimeNG inbox chips and case overview show calculated P1–P4 severity. Current residual calculation must match the current inherent assessment, latest response and latest plan. Returned rounds and obsolete reassessment scores cannot set operational severity; an unfinished reopening shows no old severity. Sample business records are excluded. Severity comes from immutable governed calculation results; risk acceptance and overrides are never inferred. Existing generic workflow visibility/routing/SLA contracts remain.
3. **Scoped operational history.** Existing native journey history includes higher-authority reopening and AVOID/ESCALATE ledgers with role, date, justification/evidence and fresh round lineage. Bilingual details use existing native cards and table. A scoped action/date audit trail shows the latest 20 events per permitted risk without global actors, metadata, hashes or unrelated records. Explicit limits are returned (20 reversals, 20 responses, 50 events per response, 20 audit events). This is bounded recent operational history, not a complete audit export, retrospective KPI cohort reconstruction or a new grant to global audit logs.
4. **Native outcome notifications and council protection.** Accepted strategy actions atomically archive prior unread outcome notices and create deduplicated bilingual notifications for the next assigned task; closure addresses its actual Risk Owner. Only in-app delivery attempts are planned. No provider call, email/webhook enqueue, fake delivery success or external message occurs. Individually addressed strategy notices exclude other people with the same role. Generic notification creation cannot impersonate this reserved AI source. Generic escalation edits reject AI strategy sources; deferred PostgreSQL validation requires the latest immutable council outcome and matching next level/role/task or governed resolved return. Existing non-AI escalation/notification behavior remains.

Existing Nest/Prisma/PostgreSQL and Angular/PrimeNG stack, explicit native AI purpose grants and append-only scoring/outcome ledgers remain. Migration `20260914100000_ai_shared_operational_contracts` adds guards only; no new dependency, permission, account, membership, password, asset state or evidence alteration. The original 4205 application/database and About DGOP remain unchanged. Original design documents/workbooks stay intact. Only the isolated 4206 AI preview receives this integration.

Shared AI case/inbox work links open the proper dedicated AI screens (including the native annual review screen). Generic case editing and decisions are hidden for protected AI cases; their backend guards remain. AI workflow type/authority-routing labels are bilingual. Full translation of older native AI workflow timeline event identifiers remains part of release verification.

Validation covers native workflow/governance regressions, API and Angular builds, clean-install/baseline-upgrade PostgreSQL/Nest/HTTP journeys, live calculation privacy, fresh reopening exclusion, both operational intake states, retained drafts, native generic/direct escalation bypasses, required-audit notification rollback, in-app-only plans, individually addressed recipients and scoped history. Final runtime/browser verification and exact test results are recorded in checkpoint.md/local verification outputs.

Next scope remains historical KPI reconstruction, authorized severity override methodology, wider treatment/notification contracts and complete bilingual multi-actor release verification. Actual-source reconciliation/pilot acceptance, production release/load/cutover and controlled original Phase 12 rollout stay open.
